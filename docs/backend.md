# Backend Architecture

Chattoneko is a single Go binary: embedded Svelte SPA + REST/SSE API + SQLite storage + one OpenAI-compatible provider + tools (integrated built-ins and MCP servers).

```
main.go                      startup wiring, flags, graceful shutdown
droproot_linux.go            container privilege drop: chown the data dir, become uid 1000 (no-op elsewhere)
internal/
  config/                    SQLite-backed config store (live snapshots, updates, model metadata)
  db/                        SQLite open, embedded schema migration
  db/query/                  sqlc-generated typed queries (queries.sql)
  store/                     persistence layer over db/query (domain types)
  provider/                  normalized OpenAI-compatible streaming client (live-swappable endpoint + /models fetch)
  llm/                       shared non-streaming client cache (title task, specialist tools, speech)
  mcphub/                    MCP server connections (streamable HTTP), live-reloadable
  tools/                     integrated tools + merged tool catalog
  engine/                    generation turn loop, per-chat SSE hubs
  titlegen/                  background chat-title task + its own SSE hub
  attach/                    file classification (extension-based media, text sniffing, filename sanitizing)
  media/                     ffmpeg conversion of uploads (every image to JPEG, every recording to mono MP3)
  webfetch/                  bot-detection-resistant URL fetching (fetch tool)
  auth/                      optional single-user JWT auth (env-var driven, plaintext password)
  api/                       HTTP routes, SSE endpoints, SPA serving, CORS
```

## Startup sequence (main.go)

1. Parse flags: `-db <path>` (default `chatto.db` next to the executable, so the same DB is used regardless of the working directory), `-listen <host:port>` (HTTP listen address, fixed for the process lifetime; default `:8080`), `-debug` (debug logging). There is no config file; everything except the listen address (flag) and single-user auth (env vars) lives in the database.
2. Configure structured logging (`slog`, text handler on stderr; `-debug` lowers the level to Debug).
3. Require ffmpeg (`exec.LookPath` over `media.Binary()`): fatal, and checked before anything is opened or created, because without it every media upload fails as `ErrUnsupported` — a 415 blaming the user's file rather than the install. `jq` is deliberately not checked here; a host without it lists the tool with `RequiresBinary` instead (see Tools).
4. Drop root when running as it (`dropRoot`, `droproot_linux.go`): make the database's directory writable by uid/gid 1000 and switch the whole process to it before anything is opened. The image starts as root only so a bind-mounted data directory needs no host-side `chown`; `syscall.Setuid` is process-wide on Linux since Go 1.16, so there is no re-exec through a su-exec-like helper and no window where a goroutine is still root — which matters because ffmpeg parses untrusted media in-process. A no-op under `docker run --user` and off Linux.
5. Create the DB file with mode `0600` if missing (chats, messages and attachments live in it), open SQLite (pure-Go `modernc.org/sqlite`, `CGO_ENABLED=0` builds), run the embedded migrations.
6. `config.NewStore` loads (or seeds on first run) the configuration from the `config` table. Auth is not in the table: it is derived from the `CHATTO_USERNAME` / `CHATTO_PASSWORD` env vars (login required exactly when both are set). `warnIfExposed` logs a warning whenever auth is disabled and the listen address is not loopback-only.
7. Startup sweeps: empty the conversion temp directory (`media.Sweep` — a conversion killed mid-run never ran its `defer`s), delete orphan attachments older than 24h (uploaded but never sent, created by a tool but never attached, or unlinked by a history truncation), delete empty chats older than 24h (created but never messaged).
8. Create the live provider wrapper (`provider.NewLive` — starts unconfigured if the endpoint isn't set yet; fail-on-call, not fail-on-start), connect the MCP hub (dead servers are skipped with a warning), and merge the tool catalog: integrated tools first, then MCP tools; integrated tools win display-name collisions. The merged catalog is computed lazily on every call so live changes are visible without rebuilding it, and it layers the configured global per-tool defaults (`tool_defaults`) over the sources' own, so the engine and the API both see the settings-UI default for every tool.
9. Create the engine on a server-scoped context — generations survive HTTP client disconnects and end only via stop, chat deletion, or server shutdown. Recover crashed generations left behind by an interrupted process (see engine section).
10. Start the title task (its own goroutine + independent SSE hub).
11. Assemble the API server with the embedded `web/dist` filesystem, bind the `-listen` address (a bind failure is fatal) and serve. The `http.Server` sets `ReadHeaderTimeout` only — no `WriteTimeout`/`ReadTimeout`, which would kill SSE.

**Build version.** `main.version` is stamped at link time (`make build VERSION=…` → `-ldflags -X main.version=…`) and handed to `api.New`, which reports it on `GET /api/meta` for the sidebar's version line. The release workflow passes the git tag (the Dockerfile strips its leading `v`, so the binary and the APK's `versionName` carry the same bare number); anything built by hand keeps the `1.0.0-local` default from the Makefile.
12. Graceful shutdown on SIGINT/SIGTERM: stop the HTTP listener (10s), then `engine.Shutdown()` (cancels active generations and waits for their final persistence), cancel the server context (stops the title task and aborts an in-flight async MCP reload's dials, so `hub.Close` cannot block on them or race their insertions), close MCP sessions, close the DB.

**Live config wiring.** `cfgStore.Subscribe` registers the reactive components once at startup: `prov.Reconfigure` re-dials the provider when base_url/api_key change, `warnIfExposed` re-checks the open-API combination, and `hub.Reload` connects/closes/reconnects MCP servers to match the new list. The reload runs async (MCP dials can take real time) and the engine then publishes a `config_changed` event on the global stream so clients refetch `/api/config` — unconditionally rather than only when the tool catalog differs, because every setting lives in that payload, and after the reload so the refetch cannot read back a stale catalog. The setup-save response goes out before the dial finishes. Engine, API, auth and the title task all read the current snapshot per request/sweep, so system prompt, limits, models, and credentials change with no restart. The listen address is NOT live-editable: it is the `-listen` flag, bound once at startup.

## Configuration (internal/config)

All configuration lives in SQLite — there is no config file and no environment variables for it. Two tables: `config(key, value, updated_at)` for global settings (structured values are JSON) and `models(model_id, endpoint, input_modality, context_length, reasoning_efforts, reasoning_default, updated_at)` for per-model metadata.

`Store` is the live handle. On first run (config table completely empty) it seeds the defaults: `system_prompt` from the embedded `internal/config/default_system.md`, `upload_max_file_bytes = 5242880`, `max_tool_iterations = 10`, `mcp_call_timeout_seconds = 60` — everything else (provider endpoint/key, model whitelist + defaults, MCP servers, tool defaults) stays empty until configured through the API. Auth is never seeded or stored: it is sourced from the environment on every load (see Auth). `Get()` returns the current immutable snapshot; `Update(ctx, Patch)` applies a partial patch transactionally, finalizes (empty/invalid values fall back to defaults, broken MCP entries and empty/duplicate whitelist entries are dropped with a warning), validates, writes the full row set in ONE transaction, swaps the snapshot atomically and notifies subscribers. `Subscribe(fn)` is how every component gets live updates (see Startup/wiring). `Complete()` reports whether provider base_url/api_key and both designated models are set — the "setup still needed" flag exposed as `setup_complete` in `/api/meta`.

Per-model metadata (`ModelMeta`): the endpoint the model is called through (`chat` — `POST /chat/completions` — the only one a model can be added on, since the audio models are free-standing ids with no row of their own; a legacy row keeps whatever it says and reads back VERBATIM rather than being coerced to `chat`, so it stays out of the picker and the settings cards instead of turning into a chat model), input modality (subset of text|image|file|audio, default `["text"]` — output is always text and is not stored), context length (default 131072), reasoning-effort levels (default `["max","xhigh","high","medium","low","minimal","none"]`) and the default effort (default: `medium`). `file` means PDF input and is its own modality because image input says nothing about it: plenty of models see pictures but refuse a PDF, and the reverse happens too. `POST /api/setup/models` fetches these from the provider's `/models` endpoint for a list of model ids and stores them, translating nothing on the way — the provider's words are ours (OpenRouter reports PDF input as `file`); fields the provider doesn't report fall back to the defaults above, and ids the provider doesn't list at all get pure defaults. Reads for ids without a stored row also return defaults.

The provider/model fields are not required for startup: a fresh server comes up in setup mode and chat attempts fail cleanly ("provider is not configured yet" / "no chat model configured yet") until the setup API fills them in.

The config snapshot carries: `system_prompt`, `provider` (base_url, api_key), `models` (whitelist, default_chat_model, default_task_model, default_vision_model, default_document_model, and the three audio fields default_transcription_model, default_speech_model and speech_voice), `mcp_servers` (name, transport http, url/headers, default_enabled), `limits`, `tool_defaults` (tool name → default enabled; the global per-tool default the settings UI edits, overriding the catalog's own default for tools it lists), `tool_titles` (tool name → user-facing label the UI shows instead of the raw name; optional, sparse, trimmed on write, and only editable for MCP tools since integrated titles are hardcoded), `auth` (enabled, username, password — all sourced from the `CHATTO_USERNAME` / `CHATTO_PASSWORD` env vars, never persisted). The listen address lives outside the snapshot (CLI flag); a designated model that is not whitelisted is cleared by `sanitizeWhitelist` — except the two audio models, which are free-standing ids and not whitelist members, so membership says nothing about them and nothing validates them (each is called through its own route, which no chat metadata describes); a designated speech model does make `speech_voice` mandatory, since `/audio/speech` requires a voice and the names are provider-specific. A designated model must also be able to do its job: `Update` clears one whose endpoint or input modalities don't cover its role — a `chat` model taking `text` for the chat and task roles, `image` for vision and `file` for the document role (`sanitizeDesignated`, reading the patch's `metas` first and the stored `models` rows behind them, since the settings sheet saves edited cards and designations in one patch). Clearing rather than rejecting is deliberate: the save lands in the same state as a missing designation, so `Complete()` goes false and the settings overlay's forced-open contract keeps the user on the page until a fitting model is flagged — no separate error mode. The vision, document and transcription models are the specialists the `vision`, `document` and `transcribe` tools hand unreadable files to, and the speech model is the one `speak` and `POST /api/speech` synthesize with: `Complete()` does not require them, a missing one only leaves that file type unreadable (the tool says so in-band), and when the vision one is empty images ride along with the chat model — as long as that model's metadata claims image input (see Attachments).

## Storage (internal/db, internal/store)

SQLite via the pure-Go `modernc.org/sqlite` driver, serialized access through `database/sql`. Schema migrations are embedded (`db/migrations/*.sql`), applied at startup in lexical order, each inside one transaction together with its `schema_migrations` record (a mid-file failure rolls back the whole file; SQLite supports transactional DDL).

Schema (embedded migrations in `internal/db/migrations/`, applied in lexical order). Every column is `NOT NULL` with a default so no query ever binds NULL:

- `config` — key/value global settings (`system_prompt`, `provider_base_url`, `provider_api_key`, `model_whitelist` (JSON), `default_chat_model`, `default_task_model`, `default_vision_model`, `default_document_model`, `default_transcription_model`, `default_speech_model`, `speech_voice`, `mcp_servers` (JSON), `upload_max_file_bytes`, `max_tool_iterations`, `mcp_call_timeout_seconds`, `tool_defaults` (JSON), `tool_titles` (JSON)), each with `updated_at`. Owned exclusively by `internal/config.Store`. (The listen address is NOT stored here — it is the `-listen` CLI flag. Auth is NOT stored here either — it is env-var driven.)
- `models` — per-model metadata keyed by `model_id`: `endpoint` (`chat` — the only value a model can be added on; a legacy row keeps its own and is skipped rather than read as a chat model), `input_modality` (JSON array of text|image|file|audio), `context_length`, `reasoning_efforts` (JSON array), `reasoning_default`. Owned by `internal/config.Store` (ModelMeta methods).
- `chats` — id (uuid), title, `title_generated` (1 = title is final: auto-title ran or the user set it manually), model, `params_json` (`{"reasoning_effort": "..."}`), `tools_json` (per-tool enable/disable overrides of config defaults), `pinned` (1 = shown in the sidebar's Pinned section; set via PATCH and deliberately never bumps `updated_at`, so pinning does not reorder the recents), created_at/updated_at (unix millis). Indexed by `updated_at DESC, id DESC` for sidebar pagination.
- `messages` — `seq` (global monotonic autoincrement, the ordering key), id (uuid), chat_id (FK, cascade delete), role (`user | assistant | tool`), status (`complete | generating | stopped | failed`), content, reasoning (JSON array with ONE entry per tool-loop turn — the turn's thinking, `""` for a turn that had none; `''` when the message never thought), error, `tool_call_id` + `name` (role=tool), model (which model produced this assistant message), `prompt_tokens`/`completion_tokens`/`duration_ms` (per-turn usage), timestamps. Indexed by `(chat_id, seq)` plus a PARTIAL index on `seq WHERE status = 'generating'` so crash recovery never scans the message table.
- `tool_calls` — id, message_id (FK), provider_call_id, name, arguments (JSON), position (generation-wide counter, so `ORDER BY position` is chronological), turn (the tool-loop iteration that produced the call — the client renders it under that turn's thinking block).
- `attachments` — id, chat_id (FK), filename, kind (`image | text | file`), mime, size (the stored bytes), data (the bytes verbatim for every kind — an image is the JPEG `internal/media` encoded, and audio is the mp3 the conversion or `speak` produced), created_at. Indexed by chat_id (chat load lists every meta). An attachment belongs to a CHAT, not to a message — which messages show it is the link table's job.
- `message_attachments` — (attachment_id, message_id) primary key, both FKs `ON DELETE CASCADE`. Many-to-many: the same file can be shown on several messages (a tool re-attaching an image the user uploaded), deleting a message unlinks its files without touching the blobs, and deleting an attachment takes its links with it. An attachment with no links is an orphan and the startup sweep reaps it — history truncation cleans up the same way, by unlinking.

`store.Store` wraps the sqlc-generated `query` package and is the only persistence interface the rest of the server uses. It exposes chat CRUD + cursor pagination + text search, message CRUD ordered by `seq`, per-message usage, chat token totals, tool-call records (including `ListDanglingToolCalls` — calls without results, used by crash recovery), attachments (create / link to a message / unlink-and-delete-when-unreferenced / orphan cleanup), title bookkeeping (`ListChatsNeedingTitle`, conditional `SetGeneratedTitle`, `MarkTitleGenerated`).

## Generation engine (internal/engine)

The engine owns every in-flight generation. Key design points:

- **Server-scoped context.** A generation runs on a child of the server context, not the HTTP request context: client disconnects never abort a generation. It ends only via user stop, chat deletion, or server shutdown.
- **One generation per chat.** Each chat has a `chatHub` holding at most one active generation. Handlers claim the generation slot BEFORE persisting anything user-visible (`ClaimGeneration` → persist → `StartClaimedGeneration`), so a concurrent request loses the claim up front with HTTP 409 instead of leaving an unanswered user message behind. Message edit is the exception: it rewrites history and re-generates, so `CancelAndClaim` stops the running generation and takes the slot in one step instead of rejecting the edit.
- **Claim/release lifecycle.** `StartClaimedGeneration` creates the assistant message (status `generating`, stamped with the model in effect at creation — the chat model can change mid-conversation) and spawns `runGeneration`. `StopGeneration` marks the generation stopped and cancels it (partial output kept). `CancelAndClaim` does the same stop, waits for the turn loop to exit (so the caller's truncation can't race its writes and strand a dangling tool message), suppresses the stopped generation's `status`/`done` events and claims the slot for the replacement. A plain re-claim can also supersede a generation mid-finalize: once its finalize starts the slot is claimable again, and the replacement installs while the old generation is still persisting — generation events are bound to the generation that produced them, so a superseded generation's terminal events are suppressed there too (they would otherwise go out under the replacement's message id and end it on the client before it streamed; the superseded one still finalizes in the DB normally). `CancelForChatDeletion` aborts without further persistence. `Shutdown` cancels everything and waits (5s cap) for final persistence so the DB close can't kill a write.

### Turn loop (runGeneration)

1. Load the chat's persisted settings → `provider.GenParams` (model, reasoning effort; model falls back to `default_chat_model`).
2. Loop: rebuild the full message list from the DB every iteration (system prompt first, then history with attachments), compute the effective tool set, stream one provider completion.
3. Drain the provider stream, publishing wire events as they happen (`delta`, `reasoning_delta`, `tool_call_started/delta/done`, each stamped with the current `turn`) and accumulating text plus THAT TURN's reasoning into the active generation — reasoning is kept as one entry per turn, never merged, so the client can render each turn's thinking where it happened. A cleanly drained turn publishes `turn_complete` (its thinking is finished; a canceled or failed stream does not). Usage tokens are accumulated across iterations; cancellation (stop) is honored promptly mid-stream.
4. If the turn produced tool calls: persist accumulated content + the calls first (crash safety, `position` continuing across turns and `turn` recording which one produced them), execute each call (`executeTools`), persist each tool result as a `role=tool` message, publish `tool_result`, announce tool-generated files (`attachment_created`), then iterate. A tool this chat does not have — toggled off, an MCP server that went away, a name the model invented — yields an explicit error result instead of executing, telling the model not to call it again. `limits.max_tool_iterations` (default 10) is that response's budget of MCP tool CALLS, not rounds: integrated tools (`Entry.Server == mcphub.BuiltinServer`) are unlimited, and every MCP call is charged whether it succeeded or failed, so a server that always errors cannot buy itself an endless retry loop. Running out never ends the generation — `executeTools` refuses over-budget MCP calls with an error result telling the model to carry on without them, so the loop always gives the model a final text round. A model that ignores that and keeps calling is bounded by `maxPostCapRounds` (3 rounds whose ONLY outcome was refusals, budget or unavailable alike — a round that ran anything at all resets the count), otherwise the loop is an unbounded spend; unbudgeted integrated tools make that count the only bound on a model insisting on a tool it cannot have. Both exits finalize cleanly, since every call has a result either way.
5. If no tool calls: finish. A truncation finish reason (`length`, `max_tokens`, `max_output_tokens`, `output_length`, `model_max_tokens`) is surfaced as a FAILED generation with a clear error instead of silently keeping a cut-off answer.

Incremental persistence: a flusher goroutine persists accumulated text/reasoning every 500ms while dirty. Finalization (`finish`) stops the flusher FIRST and waits for any in-flight flush (a stale snapshot must never overwrite final content), then — on a cancellation-detached context — synthesizes results for dangling tool calls, writes the terminal status, persists usage/duration, touches the chat, and publishes `status` + `done` (with usage) to the hub. The replay buffer is kept for a 5s grace period for late subscribers, then the hub reference is dropped and the hub pruned when nothing references it.

**Tool-call history invariant:** readers must never see a terminal assistant message with unanswered tool calls. Every exit path (complete, stopped, failed, deleted-crash) synthesizes `role=tool` results for dangling calls before finalizing.

**Crash recovery:** on startup, `RecoverCrashed` finds messages still marked `generating`, synthesizes tool results ("server restart interrupted generation"), and finalizes them as `failed` with "interrupted (server restart)".

### Effective tools

Sent to the provider per turn: enabled tools (chat's `tools_json` overrides ∪ config defaults) PLUS any tool referenced anywhere in the chat's history. The config default per tool is `tool_defaults[name]` when the settings UI set one, else the catalog's own default (integrated tools: hardcoded `DefaultEnabled`; MCP tools: their server's `default_enabled`). Omitting a disabled tool whose calls exist in history would make `chat/completions` reject the request with orphan tool_call ids — but a history-only tool is declared as a bare `(tool unavailable)` placeholder with an empty object schema, never with its real definition, whether or not it is still in the catalog: the declaration exists purely so the provider accepts the old ids, and a tool the user turned off that still arrives fully described reads to the model as an invitation to call it. Tool definitions go via the provider's native tools parameter; the system prompt carries the configured base prompt only. Not every enabled tool is one the model gets: a specialist tool declares the chat-model input modality it stands in for (`mcphub.Entry.Modality`) and drops out of the request when the model lists that modality itself, since offering a helper the model has no use for only invites a pointless round trip (reading the input modalities the generation already loaded for the attachment build). Two catalog flags are hard exclusions rather than defaults, so `enabledTools` drops them before any toggle is read and a persisted per-chat `on` cannot bring them back: `RequiresModel` (no designated model) and `RequiresBinary` (the binary the tool shells out to is absent — how a host with no `jq` loses that tool). A call naming either is refused with `unavailableText`, which counts toward `maxPostCapRounds`.

### SSE fan-out (per-chat hubs)

Every chat hub keeps: a chat-scoped monotonic event `seq`, an `epoch` (hub incarnation id — seq restarts at 1 when a hub is pruned and recreated), subscriber channels (buffer 1024), and the current generation's replay buffer.

- Generation events (`publishGen`) are appended to the replay buffer with the next seq and delivered to all subscribers. A subscriber whose buffer is full is detached (channel closed) and must reconnect — the replay covers the gap.
- Chat-level events (`user_message`, `chat_updated`, `settings_updated`, `messages_reset`) go to current subscribers; `chat_updated` is additionally replayed during the grace period so a rename landing right after `done` is not lost to a reconnecting client. A rename broadcasts `chat_updated` with just the title; a pin/unpin broadcasts it with the FULL `chat`, so a client that never loaded that row (an old chat beyond its first page) can materialize it in the Pinned section without a refetch.
- Subscribing (`Subscribe(chatID, after)`) replays every buffered event with `seq > after` losslessly; with no generation present, an `idle` event is emitted immediately.

**Global (all-chats) half.** Sidebar-relevant lifecycle events — `generation_started`, `done`, `chat_updated` — are additionally fanned out to engine-level global subscribers so clients can track background generations (breathing titles) without attaching a stream to every chat; `config_changed` and the title task's `title` events ride the same fan-out. On subscribe, clients first receive a `generating_snapshot` listing every chat with a running generation, so (re)connecting reconciles without polling.

**One endpoint, both halves.** `GET /api/stream` is the app's ONLY SSE endpoint: it always carries the global half, and `?chat=<id>&after=<seq>` additionally subscribes that chat's replayable half (the handler selects over both channels; a nil channel — no `chat` param, home view — simply never fires). Browsers cap an origin at 6 concurrent HTTP/1.1 connections, so one multiplexed socket per tab leaves the rest for that tab's fetches — a persistent socket per event class would starve them, including the send that starts a generation. **Do not add a second long-lived endpoint per tab.** A `chat` id that does not exist simply yields `idle` on its half rather than a 404 (`GET /api/chats/{id}` is what reports a missing chat; a 404 here would cut the sidebar's lifecycle events and leave the client retry-looping). Because `deliver` fans every chat event out to global subscribers too, the subscribed chat's lifecycle events arrive on BOTH halves with the same `seq` — clients dedupe by seq and drop the second copy.

Wire event vocabulary (`WireEvent`): `generation_started`, `delta`, `reasoning_delta`, `tool_call_started`, `tool_call_delta`, `tool_call_done`, `turn_complete` (the turn's stream ended cleanly — its thinking block is done), `tool_result`, `attachment_created`, `status`, `done` (carries per-turn usage + duration), `idle`, `user_message`, `chat_updated` (rename: title-only; pin/unpin: full `chat`), `settings_updated`, `messages_reset` (history truncated elsewhere — refetch), `generating_snapshot`, `config_changed`, `title` (global). `reasoning_delta` and the `tool_call_*` events carry `turn` (0-based tool-loop iteration; omitted on the wire when 0), which is what groups a turn's thinking with the calls it produced.

## Provider (internal/provider)

Talks to exactly one OpenAI-compatible endpoint via `POST /chat/completions` (official `openai-go` SDK). `types.go` defines the normalized wire contract — `Message` (role, content, images as data URLs under their stored mime, tool calls, tool_call_id), `Tool`, `GenParams` (model + optional reasoning effort, sent only when non-empty), `Usage`, and an `EventStream` of normalized events (`EventTextDelta`, `EventReasoningDelta`, `EventToolCallStart/Delta/Done`, `EventError`, `EventDone` with finish reason + usage). `chat_completions.go` implements it: builds the wire messages/tools, requests streaming with `stream_options.include_usage` (terminal usage chunk), parses deltas into the normalized event kinds, and accumulates tool-call argument fragments. Both `base_url` and `api_key` are required — fail fast instead of letting the SDK fall back to its defaults. A stream that delivers no data at all for 5 minutes is aborted (idle timeout); nothing else bounds an in-flight stream.

`provider.Live` is the swappable wrapper the engine holds: `Reconfigure(baseURL, apiKey)` re-dials only when either value changed, and empty values leave it unconfigured so `StreamChat` returns `ErrNotConfigured` instead of dialing an empty URL.

## Model metadata (internal/config, models table)

Per-model metadata (input modalities, context length, reasoning efforts) is stored in the `models` table and read live — no in-memory cache or resolver. `config.ModelMetas(ctx, ids)` returns one entry per id, substituting the spec defaults for ids without a row; `UpsertModelMetas` sanitizes (modality filter, positive context, default effort must be a listed level else falls back to the 2nd) and writes. `provider.FetchModels` pulls the provider's `/models` endpoint (15s timeout; OpenRouter-style fields: `context_length`, `architecture.input_modalities`, `reasoning.supported_efforts/default_effort`) and normalizes them; the `POST /api/setup/models` endpoint maps each requested id to provider data where available and defaults otherwise, then stores the result. `GET /api/config` exposes the stored metadata as `model_info`: one object per whitelisted model, marshalled straight from `config.ModelMeta` (`model_id`, `context_length`, `reasoning_efforts`, `reasoning_default`, `input_modality`). The same response hands the chat UI a `models.whitelist` filtered down to the chat models that accept `text` input (`chatModels`) — a legacy row on a route that is not `/chat/completions` is not a chat model and a model that can't take text can't drive a chat, so the picker offers neither — while `model_info` keeps every whitelisted model so the settings UI can still show and fix one.

## Tools (internal/tools, internal/mcphub)

Two sources merged into one catalog (`tools.Merge(cfg, sources...)`): integrated tools first (they win name collisions), then MCP tools. The merge also layers the config's `tool_defaults` map (tool name → default enabled, edited in the settings UI) over the sources' own defaults: listed tools report that default, unlisted ones keep their source's own. The same goes for the USER-facing title (`Entry.Title`, the label the chat shows instead of the raw name — never sent to the model): the config's `tool_titles` map (edited in the settings UI's MCP server cards) replaces it when it holds a non-empty value, otherwise the source's own stays (integrated tools: hardcoded `Title`; MCP tools: the title their server declared, `title` else `annotations.title` per the MCP spec). The merged catalog is the only tool interface the engine and API consume, so `GET /api/config` reports the same `default_enabled` the engine uses and a settings save applies live (both the sources and the map are read per `Tools()` call). An integrated tool that needs a designated model — the three specialists and `speak` — is LISTED while its role has none, on the same live read, but carrying `Entry.RequiresModel` (JSON `requires_model`): both tool lists render their rows from this catalog, and the settings **Tool defaults** list is exactly where someone setting the server up wants the toggle, before any model is designated. The flag is what keeps the call from ever being offered — `enabledTools` drops it before the per-chat toggles are read, so a chat that once turned it on cannot bring it back; `effectiveTools` never declares it, and a model that calls it anyway meets the turn loop's `unavailableText`, which counts as a refusal and is therefore bounded by `maxPostCapRounds` instead of being an in-band error it could retry forever. The chat's Tools panel greys the row out on the same flag (`app.toolUnavailable`), exactly like a modality-gated specialist, while the settings row stays live. A chat whose history still references such a tool gets the engine's `(tool unavailable)` placeholder, which keeps the old call id from orphaning the request.

Integrated tools (hardcoded, one file each; `tools.Builtin` lists them, each with its own user-facing `Title`):

- `time` — returns the server's current local date/time/timezone (human-readable + RFC 3339), plus its location appended as ` — <location>` when the `CHATTO_LOCATION_STRING` env var is set (non-empty after trimming). Default-enabled.
- `jq` — runs a jq filter over a JSON value the model supplies and returns what the filter produces; for arithmetic, real regular expressions and querying/reshaping structured data. It shells out to the static build `jq/build.sh` produces (`$CHATTO_JQ` when set, else `jq` on PATH, read once like `media.Binary`; the image ships it at `/usr/local/bin/jq`). A host without that binary still lists the tool, flagged `RequiresBinary` by the `Available` hook the registry reads live per catalog listing — so the engine never offers or runs it, both tool lists grey its row out, and installing jq needs no restart. `input` is a `json.RawMessage`, so the model sends the value as JSON rather than as a string holding JSON — no double-escaping and no way to hand jq malformed input, since the arguments would not have parsed. An absent `input` means `-n` (jq never reads stdin and `.` is null, which is what pure arithmetic wants); an explicit JSON null is input like any other. The filter is the only non-flag argument and `--` precedes it, so a filter beginning with a dash is not read as an option. Output is `-c` (compact, one line per value), which is the cheapest shape for a tool result and the one a model reads back without surprise.

  Sandboxing is capability-based rather than a filter inspection, resting on two facts about the invocation. `cmd.Env` is an empty slice, not inherited: jq exposes the process environment through `$ENV` and `env`, which would otherwise hand the model `CHATTO_PASSWORD` and every provider key the server was started with. And no file arguments are ever passed — the filter is the only non-flag argument — so there is no path for jq to open and `input_filename` is null. Scanning the filter text for `$ENV` would be the wrong shape: bypassed by `env|to_entries`, and it would reject legitimate filters that merely mention the word inside a string.

  Bounds: the filter at 64 KiB and the input at 1 MiB on the way in, the result at `maxOutputBytes` (shared with `fetch`) on the way out, stderr at 16 KiB, and the wall clock by the handler's context — `exec.CommandContext` kills jq when `registry.Call`'s 30s lands. Output is read with `io.CopyN` rather than collected, so a filter producing gigabytes is killed at the cap instead of buffered first; that kill makes `Wait` report a signal, which is why the truncation case is checked before the exit status and returns the truncated result rather than an error. stderr is drained through a writer that retains its first 16 KiB and discards the rest while still reporting every byte as written, because a filter raising once per input value would otherwise either fill memory with diagnostics or block jq on a full pipe until the deadline. Input is written from a goroutine with its errors dropped: jq exits without reading stdin on a compile error, and that EPIPE must not mask the real message. Every failure path returns a Go error, which the registry surfaces in-band — a missing binary, a compile error, a runtime error, a timeout and an OOM kill all reach the model as tool output. jq's own heap is the one unbounded resource (`[range(1e8)]` allocates before printing anything); a kill there is survivable because the kernel picks the largest process, which is jq, and `RLIMIT_AS` through `SysProcAttr` is the upgrade path if that proves too optimistic. The description pins the number semantics the build actually has: decNumber keeps a big literal's digits so an id survives being read and printed, but arithmetic is IEEE754 double either way and exact only within ±2^53.
- `attach` — the model hands the user a file, and showing it IS the call: the attachment is linked to the assistant message being generated before the result goes back, so a successful call always means the user can see it. Three mutually exclusive sources, validated in the handler: `content` for UTF-8 text, `content_base64` for binary the model produced (whitespace stripped and missing padding forgiven, because models emit both and a re-call costs a whole round trip), or `ids` — attachment ids already stored in this chat, which is how a file `fetch` staged reaches the screen. `filename` is required for the written sources and ignored for `ids`, whose files keep the name they were stored under. A written picture or recording is normalized on the way in by the SAME pipeline an upload goes through — `attach.ClassifyAny` reads the extension, `media.Prepare` runs ffmpeg over the bytes — so a PNG lands as a 1920px-capped JPEG and an ogg as a mono MP3, in exactly the shape a user's file does; that pipeline is `storeFile`, which `fetch` calls too. A file that will not decode is an in-band error rather than a broken thumbnail. The one difference from an upload is what happens to a file that is neither on the extension list nor text: an upload is refused, a tool's is kept as a download under `application/octet-stream`, so whatever the model found on the web still reaches the user. Both are measured against the live `upload_max_file_bytes` — a file the model writes itself gets no larger a budget than a user's upload, even though its content also has to fit in the model's output tokens. A link failure is an in-band error rather than a stored-but-invisible file: with no separate showing step there is nothing the model could call to recover. The `ids` path loads and vets EVERY id before linking any of them, so one bad id fails the call with nothing half-shown — and it cannot leave that to the link, which is chat-scoped and reports success for an id it silently linked nothing for. Ownership is therefore checked here, with the specialists' own refusal wording, which never confirms that a foreign id exists. The result names each file, its mime, size and how it renders — inline, as a text preview, or as a download — so the model describes it instead of guessing, wrapped in a `<file name=… id=… type=…>` block: a file the model attached to its own reply never re-enters the prompt, so that id is the only handle on it and is what a later `vision`/`document`/`transcribe` call about the same file is passed.

- `speak` — reads text aloud and hands the user the recording: the words go to `POST /audio/speech` under `default_speech_model` (and `speech_voice` when it is set), and whatever comes back is stored through the same `attach.ClassifyAny` + `media.Prepare` pipeline and size cap `attach` uses, then linked to the assistant message being generated — so it lands in the chat as an ordinary audio attachment the inline player already handles, and a successful call always means the user can hear it. `mp3` is what `response_format` asks the provider for, but it is not trusted: the recording goes through the audio conversion like any other, and ffmpeg probes an audio file's CONTENT rather than its name, so a provider that answers with a wav or an ogg still lands as the mono MP3 the stored mime claims; the voice is required by the settings as long as a speech model is designated, because `/audio/speech` demands one and no default fits every provider. Like `attach` it needs the chat/message coordinates, and like the specialists it reports a missing designation in-band instead of failing the generation. Its result carries the recording in the same `<file … id=…>` block, so "transcribe that back" has an id to pass.
- `fetch` — the model passes any http(s) URL and gets the body back; `webfetch.Fetch` downloads it in memory with a browser-impersonating client (bogdanfinn/tls-client: a uTLS ClientHello and HTTP/2 framing whose JA3/JA4 and Akamai fingerprints match the pinned Chrome profile, plus hand-maintained header values and on-the-wire order for that same profile, shared cookie jar). https goes through that client; plain http uses a stock client with the same headers (there is no handshake to fingerprint). Both speak bogdanfinn/fhttp — the net/http fork tls-client is built on, and the only one of the two that can put request headers on the wire in a chosen order. Both share the SSRF defenses (pre-request address check, vetting dial function, per-hop redirect policy) and request only `gzip`, which is the one encoding unpacked in-package. The body is classified by CONTENT, not by Content-Type or extension. Printable UTF-8 comes back verbatim, truncated at the 1 MiB tool-result budget (cut on a rune boundary, the cut announced with the true total) — the data-as-intermediate-step path, e.g. a JSON API response the model then queries with `jq`. Anything else is STORED as an attachment of this chat and its id comes back inside a `<file>` block instead of bytes the model cannot read: a picture, a PDF, an archive, whatever the URL served. A text body the budget cut is stored in full alongside its prefix for the same reason — the model only read the first megabyte, and the id is how the rest still reaches the user; a store failure there keeps the truncated text, because losing the file beats losing what was read. Storing goes through the same `storeFile` pipeline `attach` uses, which is what makes a fetched file readable rather than merely stored: a PNG lands as the JPEG `vision` accepts and an ogg as the MP3 `transcribe` accepts, instead of a row both refuse in-band. It is capped by the live `upload_max_file_bytes` even though the download itself is capped far higher (`attach.MaxRawUploadBytes`), and the refusal is in-band. `Timeout` is 2 minutes rather than the integrated tools' 30s, because ffmpeg may run over the body.

  A stored file is shown on NO message, and that is the design rather than an oversight: `publishNewAttachments` announces only attachments linked to the generating message, the UI has no affordance for a staged one, and the startup sweep deletes unlinked attachments after 24h (`DeleteOrphanAttachments`). So the result says out loud that the user cannot see the file yet and names `attach` as the call that shows it — without that sentence a model announces a download it never handed over, which is the one failure this split can produce that the user cannot diagnose. An empty body is an error, and with no chat coordinates to store into a binary body falls back to the old in-band refusal naming the served type and the size. Robustness details: the Accept list is a Chrome navigation list minus avif/svg so content-negotiating CDNs (imgix `auto=format`) serve WebP or PNG, two formats the conversion decodes; MediaWiki thumbnails whose width the wiki rejects with HTTP 400 fall back once to the original file URL.

  Stored-file naming: the final URL's last path segment (through `attach.CleanFilename`, then capped at `attach.MaxFilenameBytes` with the extension preserved); media get the suffix of what the conversion produced (`song.wav` → `song.mp3`, `cat.jpeg` → `cat.jpg`), and an extension-less URL (an API path like `/repos/x/y`, a CDN's `/image/1234`) gains the suffix its served Content-Type implies via `attach.ExtForMime` — load-bearing rather than cosmetic, because the suffix is what DECIDES the file: a body served as `image/jpeg` becomes a picture only because it is named `.jpg`. A type that table does not know leaves the name bare, and a bare-named binary is a download. Nothing is decoded before the conversion, so a corrupt payload is ffmpeg's error to report.

  No integrated tool's LLM-facing text names another one (`TestNoCrossToolReferences` guards `attach`, matched on word boundaries because "attachment" is a word the specialists cannot do without), with one deliberate exception: `fetch`'s RESULT names `attach`, because a file stored on no message is a file the user never gets and the model has to be told what shows it. A result may name a tool where a description may not — it is the next step for a file that already exists, not a standing promise — so an `attach` tool the user turned off leaves a fetched file staged for the sweep instead of losing the read. Refusals are bounded: a round in which EVERY call was refused, whether for a tool this chat does not have or for being past the MCP budget, counts toward `maxPostCapRounds`, so a model that keeps insisting cannot spin forever. A history-referenced tool that is not enabled is declared to the provider as a bare `(tool unavailable)` placeholder rather than with its real definition — the declaration is only there so old `tool_call` ids are accepted, and a disabled tool that still looks callable is an invitation the model takes.
- `vision`, `document`, `transcribe` — the specialist tools: each hands a file the chat model cannot read to a model that can, and returns that model's answer (for audio, the transcript) as the tool result. All three come from one loop over the `specialists` table in `internal/tools/specialists.go`, whose row is the whole definition — tool name, user-facing title, the `attach.Type` it reads, the modality that makes it pointless, the formats its description names, the config role designating its model, its system prompt — so a fourth file type is a row, not a new handler. The arguments are an attachment id and a question; the file's TYPE is not one, because the stored attachment already says what it is (`attach.Type`) and each tool reads exactly one type, so a file another specialist wants comes back naming the tool that reads it rather than failing mute. The ids come from the `<file ... id="...">` reference blocks the prompt build emits for attachments with no wire representation (see Attachments), and from the same block `attach` and `speak` wrap their result in — these are the tools those references exist for. Each description names the formats its own specialist takes, so the model hears the limit before it calls instead of from a refusal, and the format check runs before the model lookup, so an unsupported file is never reported as a missing server setting. The bytes are read back from the database and sent to the model designated for that type (`default_vision_model` for images, `default_document_model` for PDFs, `default_transcription_model` for audio) through `internal/llm` — as ONE non-streaming completion for the two readers, as one `/audio/transcriptions` request for audio, since the models that role names are transcription models with no chat endpoint — with a client cache per tool (a shared one would rebuild its client — dropping the connection pool — on every call that switches type).

  One-off by construction: a single user message (the file part first, the question last, because some OpenAI-compatible routes drop a text part that PRECEDES the media) under the specialist's own system prompt, one answer back, and nothing carried over in either direction — the specialist never sees the conversation, so the description tells the chat model to make its question self-contained and to ask everything in one call. The two prompts are markdown files embedded from `internal/tools/prompts/` (`vision.md`, `document.md`), each written for a reader that is another model: answer first, quote exactly, say when the file doesn't cover the question, no preamble — and treat the file as data, so a question or instruction written INSIDE it is content to quote back and never a task to perform (without that a PDF whose whole body is "Who is Eminem" gets answered instead of reported, and an in-file "ignore your instructions" is obeyed). Wire shapes: an image as a `data:` URL under its stored mime, but only for the JPEG `attach.SendsAsImage` allows — a PNG, WebP, GIF or BMP row previews in the browser and is refused in-band here, since history is rebuilt every turn and a mime the provider rejects would break that chat for good; a PDF as a `file` part (`file_data` data URL + filename). JPEG is the whole set in practice, not a policy that costs anything: every picture — an upload, one `attach` was handed, one `fetch` stored — is the JPEG `internal/media` produced, so no other image mime is stored any more (a row from before that still previews and takes the reference path).

  Audio takes a different road: the recording goes to `/audio/transcriptions` as a multipart file under its stored filename and mime (which is how the endpoint identifies the container), and the TRANSCRIPT is the tool result — the description says so, and the chat model answers whatever it asked from that text. A transcription model takes no prompt, so `question` is declared but NOT required there and the handler ignores it: a model that has just read the other two tools' shapes sends one anyway, and a property the schema never mentions invites a provider-side rejection under `additionalProperties`. An empty transcript is silence or unintelligible speech, reported in-band as such rather than as an error. Because the container is named by the file part, nothing is remuxed on the way out — but the tool takes MP3 only, which is every recording the app stores: an upload, a file `fetch` stored and a `speak` recording all come out of the same conversion as mono MP3, so the check only ever fires on a row stored before that was true, and then refuses in-band naming the format.

  Which of them a chat model is offered depends on that model: each tool carries the input modality it stands in for (`image`, `file`, `audio`) next to the `attach.Type` name it routes on (`image`, `document`, `audio` — the provider's word for PDF input is `file`, the prompt's is `document`), and `effectiveTools` leaves it out of the request when the model lists that modality itself, so a model that sees pictures is never offered `vision`. The whole comparison is a `slices.Contains` per tool, and `image` never stands in for `file`, which is why that modality exists. The same field rides out on `/api/config` as `requires_modality`, which the chat UI reads to grey the row out for the picked model (see frontend) — a tool that is unavailable, not merely off. Every other catalog entry leaves it empty and is always offered.

  An attachment is readable only inside its own chat: an id belonging to another one is answered with the same "no attachment with id" text as a plain miss, so a result never confirms that a foreign id exists. Everything else that can go wrong is an in-band error the chat model can react to and relay — no model designated for that type, provider not configured, a text file (no specialist needed: a user's text is already in the conversation, and a file the model created it wrote itself), a binary no specialist reads, and an EMPTY answer, which carries the provider's own `finish_reason` and token counts because a reasoning model can spend the whole `max_tokens` budget (4096) on hidden reasoning and return nothing but a `length` finish.


Every integrated call is bounded by a context timeout — the hardcoded 30s default, or the tool's own `Timeout` when it does remote I/O (the specialists get 5 minutes, being a full LLM round trip over a file) — and wrapped in a panic recovery, so an in-process handler surfaces as an in-band tool error rather than killing the generation or the process. Handler errors are returned in-band (`isError=true`) exactly like MCP tool errors.

MCP hub (`mcphub`): connects every `mcp_servers` entry at startup (streamable HTTP transport with optional headers), 30s connect timeout per server; a dead server logs a warning and is skipped. Each connected session lists its tools, which become catalog entries with config-driven `default_enabled`; two servers exposing the same tool name are resolved first-in-config-order-wins (the later entry is dropped with a warning, not aliased). `Call` dispatches by display name to the owning source, bounded per call by `mcp_call_timeout_seconds`. `CallMeta` (chat id + owning assistant message id) lets integrated tools attach artifacts to the right message; MCP tools ignore it. `mcphub.Probe(ctx, serverConfig)` is the same dial-and-list outside any hub — one throwaway session, closed before it returns — so the settings UI's per-server-card **Fetch** button can list a server that is brand new or has unsaved url/header edits without touching the live connections or the catalog.

## Title generation (internal/titlegen)

Background task that is the ONLY writer of auto-generated titles. A polling loop (1s cadence, at most 16 chats per sweep) finds chats with `title_generated = 0` and picks the source from the first user message: its text (capped at 1000 runes) goes to `GenerateFromText`; a text-only first message goes to `GenerateFromFile` with the filename + content; an image-only first message gets the fixed title `User Image Input` with no model call. The model call uses a dedicated NON-streaming client (same provider endpoint, task model + its stored default effort, `max_output_tokens = 1024` so reasoning models can't spend the whole budget before emitting content, 30s per-call timeout). Transient failures retry after a fixed 10s delay, at most 5 attempts per chat, after which the chat keeps "New Chat". The result is capped at 60 runes and written conditionally (`SetGeneratedTitle` only while `title_generated = 0`) — a concurrent manual rename wins; the task then marks the title final either way.

Results are handed to a publish callback (wired to `Engine.PublishTitle`), which fans them out as `title` events on the global half of `/api/stream` — the task itself still shares no locks, channels or buffers with the generation machinery, so a stalled generation cannot delay a title. Title events are self-contained (chat id + title) and idempotent — no replay buffer needed: a dropped one costs a stale sidebar label until the next chat-list load (which focus/visibility triggers).

## Attachments (internal/attach, internal/media)

One rule, two thresholds. Every file is classified by its EXTENSION alone (`Classify`): the name is trusted, no byte of a media file is sniffed, and whatever the extension claims is converted to the one shape the database stores before it is written (see Conversion below). Anything without a media or PDF suffix has to pass the text heuristic (`IsText`: no NUL byte, valid UTF-8, ≥95% printable/whitespace runes). What is left is where the two paths part: an **upload** refuses it (`ErrUnsupported` → HTTP 415), while a **tool's** file (`ClassifyAny`) keeps it as a download under `application/octet-stream` — the mime the attachment handler serves every non-audio binary as anyway — so whatever a model found on the web still reaches the user, it simply has no preview and downloads on click. A refusal names the accepted list, rendered from the extension sets themselves (`acceptedExts`) so the prose cannot drift from them.

The accepted extensions (`attach.imageExts`/`audioExts`, the same list the browser stages against in `web/src/lib/media.js`): images `png bmp tga jpg jpeg gif webp`, audio `wav mp3 ogg oga opus webm mkv mov flac alac m4a m4b mp4 aac`, plus `pdf` and text. A video container counts as audio — no picture survives the conversion, only the soundtrack, and a video with no audio track is refused like any other undecodable file. `tiff` is deliberately absent (the ffmpeg build ships no TIFF decoder) and so is `ico`: both are refused by the name, while an unsupported codec inside an ACCEPTED container is refused by the conversion.

Raw reads are capped at 64 MiB per file (`MaxRawUploadBytes` — also the constant the HTTP layer sizes its multipart ceiling from, and the ceiling a conversion's output is re-checked against). The per-file stored cap (`limits.upload_max_file_bytes`) is measured against the bytes that land in the database: directly for text and PDF, and after the conversion for media, so a 40 MB shot that converts to a 2 MB JPEG is accepted and one that converts to something over the cap is refused (HTTP 413). The multipart handler checks the size the header already carries against the raw ceiling before reading a file's bytes at all. A rejected file in a multi-file batch rolls back the ones already stored — orphans are only swept at startup. One file's ffmpeg run is bounded by a 2-minute context (`convertTimeout`): the server carries no `WriteTimeout` (it would kill SSE), so nothing else stops a wedged conversion. `media.run` reports that kill as the context error rather than as `ErrUnsupported`, which keeps it a 504 here and stops the tool paths from telling the model that a cut-short file was undecodable.

The stored NAME is the conversion's: an image always ends as `.jpg` and a recording as `.mp3`, whatever suffix arrived (`photo.jpeg` → `photo.jpg`), because the name has to match the bytes. Text and PDF keep theirs; a text file's mime comes FROM its extension (`textExts`), which is why rewriting it would be circular. Filenames are sanitized (`CleanFilename`).

### Conversion (internal/media)

Every picture is stored as a JPEG and every recording as a mono MP3, produced by running ffmpeg over the invocations in `ffmpeg/cli.md`: images capped at 1920 on the long side (1080 for a portrait one), never upscaled, first frame only, encoded at quality 90 (`-q:v 3` on ffmpeg's inverted mjpeg scale, measured against `cjpeg -quality 90`) with `-pix_fmt yuvj420p` forced because mjpeg picks its quantization table per pixel format and its own 4:4:4 default writes one three times coarser at the same `-q:v`, `-max_pixels 33177600` bounding the decode of a header that claims absurd dimensions; audio to 1 channel, 22050 Hz, 32 kbps with the metadata dropped. `media.Prepare` is the one entry point — an upload, `attach`, `fetch` and `speak` all hand it a `Classify` verdict and get back the bytes to store plus the stored cap applied — so there is a single set of invocations behind every attachment the app holds. The binary is `$CHATTO_FFMPEG` when set, else `ffmpeg` on PATH — the image ships the static build `ffmpeg/build.sh` produces at `/usr/local/bin/ffmpeg`, a dev machine uses its own. `main` requires it: a failed `LookPath` is fatal at startup, before root is dropped or the database is created, because a missing ffmpeg would otherwise surface as a 415 blaming every file the user uploads.

Conversion always goes through two temp files under `$TMPDIR/chattoneko-media`, both removed before the call returns whatever it returned: ffmpeg needs a NAMED input (TGA has no magic bytes at all, so the `.tga` suffix on the temp file is the only thing that reaches its decoder, and an MP4 whose `moov` box sits at the end demuxes to nothing from a non-seekable pipe) and a named output (an MP3 written to stdout loses its Xing header). `os.CreateTemp(dir, "conv-*"+ext)` replaces the `*` and keeps the suffix, which is what preserves the extension. No file on the filesystem is ever served: only the converted bytes in the database are. A conversion killed mid-run (OOM, SIGKILL, deploy) never ran its `defer`s, so `media.Sweep()` empties the directory at startup — the directory is the app's alone, which is what makes that safe, and the whole janitor. A non-zero exit means no usable output, and ffmpeg's own one-line diagnosis is wrapped in `ErrUnsupported` (→ 415): a file that lies about its extension is rejected by the conversion rather than by a byte check. Runs are single-threaded and bounded by the request context, never by stdin.

Every attachment is stored whatever the model can do with it, and the prompt build decides how it appears. Text attachments are serialized into the user message as delimited `<file name="..." id="..." type="...">` blocks (`SerializeText`; only on USER messages — a file the model attached to its own reply never re-enters the prompt, and instead gets its id from the `<file>` block `attach`/`speak` put in their tool result, which history replays every turn). Images go out as `data:<stored mime>` content parts when the chat model's stored metadata lists `image` input AND the mime is JPEG (`inputModalities`, read once per generation, re-evaluated when the chat switches model; `attach.SendsAsImage` gates the mime, so a JPEG, WebP, GIF or BMP row takes the reference path instead of 400ing every turn of that chat), and as a `<file>` REFERENCE when it doesn't. Binary files have no wire representation at all and always take the reference path. `SerializeRef` keeps the same envelope — filename, the unguessable id repeated in the closing tag — but the body says the content is not included and names the mime, size and the attachment id the bytes live under, so a later tool can be handed that id as an argument — which is exactly what the specialist tools do: they load the bytes back and ask a model that CAN read them (see Tools). Both serializers carry a `type` attribute from `attach.Type`: `image`, `text`, `audio`, `document` (PDF) or `file` for any other binary — the kind decides for the first two, the stored mime inside the binary kind for the rest. A failed metadata lookup counts as text-only: losing a picture beats a provider 400 on an endpoint that takes none.

Serving: images inline under their stored mime — JPEG for anything the conversion produced, the raster mime a row stored before it was converted still carries, none of which can carry script, and an SVG never reaches that branch because it classifies as text; text as `text/plain` and every other binary as `application/octet-stream`, both regardless of the stored mime (a stored HTML or SVG can never execute in the app's origin, and octet-stream also makes the browser download instead of preview) with the real filename via `Content-Disposition`. Audio is the single exception to the binary rule and keeps its stored `audio/*` mime: it cannot execute, and the chat's inline player needs a real type (Safari refuses to play octet-stream, and `/api/attachments/{id}` carries no extension for the browser to guess from). The disposition stays `attachment` — a media element ignores it, a navigation still downloads.

## Auth (internal/auth)

Optional single-user auth, driven entirely by environment variables — there is no settings toggle. Login is required exactly when **both** `CHATTO_USERNAME` and `CHATTO_PASSWORD` are set (non-empty after trimming); if either is missing, auth is OFF and the app is fully open. The password is used as **plaintext** and is never written to the database. Auth is read once at startup; changing it means setting the env vars and restarting. When enabled:

- Login (`POST /api/auth/login`) verifies the credentials against the env-configured username/password and returns a signed JWT (HS256, 90-day TTL). Login attempts are rate-limited by an in-memory token bucket (5/min, burst 5), and both username and password are compared in constant time so a wrong username costs the same as a wrong password (no enumeration timing channel).
- The credentials live only in the process environment (`CHATTO_USERNAME` / `CHATTO_PASSWORD`) — they are never persisted to the config table and are not exposed through the setup API.
- The JWT signing key is derived from the credentials (`sha256("chattoneko-jwt:" + username + "\x00" + password)`), so tokens survive restarts and changing the env password invalidates every outstanding token. Tokens are stateless: no server-side session store, no logout invalidation — clients discard the token to log out.
- Requests are admitted with `Authorization: Bearer <token>`, or (GET only) `?token=` — EventSource streams and `<img>` attachment loads can't set headers. Only HS256 is accepted (no algorithm downgrade).
- `GET /api/meta` (auth_enabled + setup_complete flags + the build version) and login are public; every other `/api/*` route goes through the auth middleware. Expired tokens get a 401 and the clients (web + mobile) drop back to the login screen.

| `PUT /api/setup` | partial config update — only provided fields change (any `auth` field is ignored). `models.metas` upserts per-model metadata (models dropped from the whitelist lose theirs); `tool_defaults` replaces the whole global per-tool default map and `tool_titles` the whole user-facing title map (blank titles are dropped, so clearing a box hands the label back to the catalog). Returns the full config. |
| `POST /api/setup/models` | accepts `{"model_ids":[...]}`; fetches the provider's `/models`, stores per-model metadata (defaults where unreported), returns the stored rows + per-id source |
| `POST /api/setup/mcp/tools` | accepts ONE MCP server's `{name, url, headers}` — unsaved settings-form values are the point — and returns its tools as `[{name, description, title}]` via `mcphub.Probe` (`title` being what the server itself declared, the card's title-box placeholder). Saves nothing, connects nothing, leaves the live catalog untouched; 400 without a url, 502 when the server can't be dialed or won't list. |
| `GET /api/chats` | cursor-paginated chat list (`limit`, `before`, `before_id`) or `?q=` text search; the first page (no cursor) also returns `pinned`, the complete pinned list |
| `GET /api/stream?chat=<id>&after=<seq>` | the ONE SSE endpoint: all-chats lifecycle + title events, plus chat `<id>`'s replayable half when `chat` is given |
| `POST /api/chats` | create empty chat ("New Chat"; optional model/params/tools) |
| `GET /api/chats/{id}` | chat + messages (seq-ordered) + `active` + token totals |
| `PATCH /api/chats/{id}` | rename, per-chat settings, and/or `pinned`; broadcasts `chat_updated` (rename: title; pin: full chat) / `settings_updated` |
| `DELETE /api/chats/{id}` | cancels an active generation, deletes the chat (cascade) |
| `POST /api/chats/{id}/messages` | send: claim → persist user message (+ link attachments) → broadcast → start generation (409 if a generation is active) |
| `PATCH /api/chats/{id}/messages/{mid}` | edit a user message (optional attachment keep-list), truncate everything after it, re-generate; stops an active generation for the chat first rather than answering 409; broadcasts `messages_reset` |
| `POST /api/chats/{id}/regenerate` | delete the last assistant message + everything after it (their attachment links cascade away), re-generate; broadcasts `messages_reset` |
| `DELETE /api/chats/{id}/generation` | stop the active generation (partial output kept) |
| `POST /api/chats/{id}/attachments` | multipart upload, field `files` (≤8 files): classified by extension, media converted before it is stored (415 for a format or a file that will not convert, 413 over a cap, 504 if a conversion times out), one bad file rolls back the whole batch |
| `GET /api/attachments/{id}` | stored bytes (images inline under their stored mime; text/plain, octet-stream or the stored audio mime as a download) |
| `POST /api/speech` | accepts `{"message_id":"..."}`, synthesizes that message's content and streams the mp3 back. Nothing is stored — it is a rendering of text the database already holds — and a missing message is 404, an empty one 400, no speech model or provider 503, a provider failure 502 carrying its own diagnostics |

Cross-cutting:

- Every JSON response carries `Cache-Control: no-store` — config is live-editable, so a cached whitelist would outlive the change.
- JSON request bodies are capped at 1 MiB (`MaxBytesReader`, over-cap → 413, malformed → 400); multipart uploads have their own ceiling (raw per-file cap × files + 64 KiB overhead).
- SSE handler writes `event: message` + JSON `data` lines, flushes every event, and sends a `{"type":"ping"}` event every 20s. It is a real event, not an SSE comment, because EventSource never surfaces comments: the client uses the pings to detect a half-open socket (60s of silence → reconnect). Long-lived SSE paths are excluded from request logging.
- The claim → persist → start handlers (send, edit, regenerate) run their persistence on `context.WithoutCancel(r.Context())`: once the claim is taken, a client that disconnects mid-request (app killed on a slow link) must not strand a user message without a reply or a truncated history without its regeneration. The generation itself already runs on the server context.
- CORS middleware permits only the Capacitor WebView origins (`http://localhost`, `https://localhost`, `capacitor://localhost`) — the embedded web UI is same-origin and needs none; credentials stay off (the mobile app authenticates with Bearer tokens). Preflights are answered before routing/auth. Every response — allowed origin or not, including the origin-less `<img>`/`<a>` loads — carries `Vary: Origin`, so a cached attachment response without CORS headers can never be replayed to a later cross-origin `fetch()` of the same URL.
- SPA handler serves the embedded `web/dist`: hashed `assets/*` are immutable-cached; everything else is `no-cache`, with HTML falling back to `index.html` for client-side routes; unknown `/api/*` paths get a JSON 404.
- Request logging middleware records method/path/status/duration (5xx = error, 4xx = info, routine chat traffic = debug). The status recorder forwards `Flush` and `Unwrap` so SSE and `http.ResponseController` keep working through it.
